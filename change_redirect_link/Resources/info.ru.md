# Подмена ссылки

Прогулявшись по сайту, можно найти все запросы, связанные с переходами на другие страницы. В приложении встречаются следующие значения параметра `page`: 

- `page=survey`
- `page=member`
- `page=upload`
- `page=searchimg`
- `page=media`
- `page=recover`
- `page=signin`
- `page=feedback`
- `page=redirect`
- `page=b7e44c7a40c5f80139f0a50f3650fb2bd8d00b0d24667c4c2ca32c88e13b758f`

В основном здесь только переходы на страницы текущего сайта. Исключение — параметр со значением `redirect`, где используется ссылка на социальные сети.

Полный пример такого URL:

```bash
index.php?page=redirect&site=instagram
```

Вероятно, `instagram` — это значение переменной `site`.

Пробуем подменить её на адрес любого другого сайта, например:

<http://<IP>/index.php?page=redirect&site=https://web.telegram.org/>

В результате приложение выполняет переход и выдаёт флаг.

## Предполагаемая логика на стороне сервера

Ниже приведён пример того, как примерно могла бы выглядеть обработка таких редиректов в бекенде.

```bash
const socialMedia = {
    facebook: url,
    twitter: url,
    instagram: url,
}; // Если, конечно, адреса сохранены в коде, а не в env или на proxy.

app.get('/', (req) => {
    if (req.params.page === 'redirect') {
        switch (req.params.site) {
            case "facebook":
                redirectTo(socialMedia["facebook"]);
            case "twitter":
                redirectTo(socialMedia["twitter"]);
            case "instagram":
                redirectTo(socialMedia["instagram"]);
            default:
                redirectTo(req.params.site);
                /*
                Здесь проблема: неопознанный адрес, который не сохранён в приложении как разрешённый,
                должен обрабатываться как ошибка 404 либо не должен обрабатываться вообще, как в intra42.
                То есть должно быть:

                default:
                    return; // do nothing
                */
        }
    }
})
```

Проблема заключается в том, что приложение выполняет редирект на значение, которое контролируется пользователем. Если адрес не входит в список разрешённых, запрос всё равно обрабатывается и пользователь перенаправляется на внешний ресурс.

## Возможные последствия

Пользователь ожидает, что попадёт на сайт социальной сети, а по факту его отправляют на вредоносный сайт, который может выглядеть похоже или даже точно так же, как настоящий ресурс. Если пользователь невнимателен, он может ввести на этом ложном сайте свои учётные данные, которые впоследствии будут украдены. Так же ссыдка может ввести на эндпоинт скачивания вредоносного файла.

Обычно, когда пользователь наводит курсор на ссылку, в нижнем левом углу браузера появляется подсказка с указанием того, куда ведёт эта ссылка. Если обращать на это внимание, можно заметить подмену и защититься от неё.

## Классификация уязвимости

Такой сценарий часто используется в фишинговых атаках. В OWASP данная уязвимость относится к категории A01:2025 и классифицируется как [CWE-601](https://cwe.mitre.org/data/definitions/601.html).
